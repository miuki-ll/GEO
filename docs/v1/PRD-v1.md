# GEO 多企业 AI 可见度运营平台 — 产品需求文档 v1.1

> **文档状态**：历史版本，已被 **PRD-v2.md** 取代  
> **更新日期**：2026-07-01  
> **MVP 垂直行业**：生美机构（`beauty_local` 行业包，默认生美合规）  
> **产品定位**：多企业 SaaS，基于知识库 + Agent 编排，完成「分析 → 生成 → 发布 → 监测 → 迭代」闭环

---

## 1. 背景与问题

在 AI 搜索时代，用户 increasingly 通过豆包、DeepSeek、Kimi 等 AI 获取选购建议，而非仅依赖传统搜索引擎。品牌竞争从「被搜索到」转向「被 AI 引用、被用户采信」。

**核心问题：**
- 企业不知道 AI 如何描述自己的品牌
- 缺乏结构化、可验证的内容资产
- 各平台内容形态不同，无法一键通发
- GEO 效果难以监测与归因

**我们要做的：**
帮多个企业，基于各自知识库，自动生成 AI 可引用的高质量内容，半自动发布到各信源，并持续监测 AI 可见度、迭代优化。

**不是什么：**
- 不是批量铺量的 AI 软文工厂
- 不承诺「AI 排名第一」
- 不承诺全自动发到所有第三方平台

## 3. 目标用户

### 3.1 MVP 目标用户

**生美机构**（本地生活 + 专业信任混合场景；MVP 默认按生美合规）

- 单店 / 连锁皮肤管理、生活美容门店
- 有明确服务项目（皮肤管理、补水、清洁、基础光电等；不做医疗效果宣传）
- 需要在 AI 回答「[城市]哪里做 XX 好」「[品牌]怎么样」时被提及

### 3.2 平台级用户角色

| 角色 | 说明 |
|------|------|
| Owner | 企业所有者，全部权限 |
| Admin | 管理知识库、确认策略、发布 |
| Editor | 编辑内容、提交审核 |
| Viewer | 只读报告 |

**账号模型：** 一企业多账号；一个用户账号可关联多个企业（预留代理商场景）。

## 4. 用户旅程（3 步）

```
Step 1：录入企业信息
  → 填写 / 导入知识库（品牌、门店、项目、竞品、案例等）

Step 2：确认策略与内容
  → AI 分析 → 出策略报告 → 用户确认 / 修改 → 生成多版本内容

Step 3：发布并查看效果
  → 发布（自动 + 半自动）→ 监测 AI 可见度 → 查看报告 → 迭代
```

**关键原则：** 策略必须经用户确认后才执行内容生成与发布，不允许 AI 自动对外发布。

## 5. 系统架构概览

```
接入层        Web 管理台
              ↓
租户层        企业 / 账号 / 权限 / 套餐
              ↓
核心层        知识库 │ Orchestrator Agent │ Skill 运行时 │ 审核 │ 任务流
              ↓
行业层        beauty_local 行业包（MVP）│ 其他行业包（预留）
              ↓
基础设施      LLM │ 向量库 │ 存储 │ 定时任务
```

### 5.1 三层关系

| 层级 | 职责 | 变更频率 |
|------|------|---------|
| **平台层** | 租户、知识库、Agent、Skill、发布、监测 | 稳定 |
| **行业包层** | 字段 Schema、Skill 集、Prompt、合规、渠道策略 | 按行业扩展 |
| **企业层** | 各企业知识库、策略、内容、监测数据 | 每企业独立 |

### 5.2 行业包（Industry Pack）说明

行业包 = 某一行业的可插拔配置包，包含：

- 知识库字段扩展（如：项目、仪器、资质）
- 行业专用 Skill 清单
- 行业 Prompt 模板（Layer 2）
- 信源优先级与发布渠道包格式
- 监测 Prompt 模板
- 合规规则（MVP 默认生美；医美分级规则预留）

MVP 仅实现 `beauty_local`（生美默认）；后续新增行业 = 新增行业包，不改平台核心。

## 7. 知识库（M2）

### 7.1 设计原则

- **唯一事实源：** 所有生成内容的数据必须可追溯到知识库
- **分层结构：** 品牌级 + 门店级
- **禁止幻觉：** 无来源的数据不得写入内容，标记「待补充」

### 7.2 通用字段（平台层）

| 类别 | 字段 |
|------|------|
| 品牌 | 品牌名、简介、定位、联系方式 |
| 门店 | 名称、地址、电话、营业时间、坐标 |
| 竞品 | 竞品名称、URL、备注 |
| 案例 | 背景、方案、结果（需真实可验证） |
| 资质 | 营业执照、医疗许可等 |
| 资产 | 上传文档、图片 |

### 7.3 美容行业扩展字段（beauty_local）

| 类别 | 字段 |
|------|------|
| 项目 | 名称、描述、价格区间、适用人群、注意事项 |
| 仪器 | 品牌、型号、认证 |
| 合规 | 生美 / 医美分类（MVP 默认生美） |

### 7.4 痛点挖掘（多形式输入）

痛点挖掘不等于「只能爬虫」。平台采用**多源采集、按优先级合并**：

| 优先级 | 输入方式 | 说明 | 是否爬虫 |
|--------|---------|------|---------|
| P0 | 客户自有数据 | 客服记录、销售话术、门店 FAQ、用户反馈导入 | 否 |
| P1 | 手动录入 / 表单 | 运营补充竞品、常见问题 | 否 |
| P2 | SEO / 问答数据 API | 5118、新榜等关键词、问答热词 | **不是爬虫**，是付费数据服务 |
| P3 | 定向公开页采集 | 竞品官网公开页、行业垂直站 | 是（受 robots.txt 约束，低频） |

**原则：** 有客户数据用客户数据；没有再用 API；爬虫只做补充，不做全网无差别抓取。

`beauty_pain_mine` Skill 输出：痛点列表 + 高频问题 TOP N + 数据来源标注。

### 7.5 多门店

- 支持 1 品牌 N 门店
- 门店继承品牌信息，可覆盖：地址、营业时间、特色项目、价格
- MVP：至少支持 NAP（名称/地址/电话）+ 门店级项目差异（可后续迭代）

## 8. Agent 体系（M3）

### 8.1 Agent 分工（MVP）

```
Orchestrator Agent
  读知识库 + 行业包 → 输出策略草案 + Skill 执行计划

Review Agents（策略确认前）
  ├── 合规审查：广告法、医美禁词
  └── 事实审查：内容是否有知识库依据

用户确认 + 人工修改
  ↓
Skill 运行时执行
```

### 8.2 策略报告内容

- 业态画像（如：生美 / 医美、单店 / 连锁）
- 痛点列表
- 内容缺口
- 渠道计划（发哪里、什么形态）
- Skill 执行计划
- 监测 Prompt 计划
- 风险标注（合规 / 事实问题）

### 8.3 路由逻辑

- **不在注册时选手行业**
- 用户提交知识库后，Orchestrator 自动识别业态并匹配行业包
- 用户可 override 分析结果

### 9.1 Skill 定义

```
Skill = Prompt 模板 + Tools + 输入输出规范 + 约束规则
```

### 9.2 三层 Prompt 结构

| 层级 | 来源 | 说明 |
|------|------|------|
| Layer 1 | 平台 Skill | 通用写作规范、防幻觉约束 |

| Layer 3 | 企业知识库 | 品牌、项目、城市等动态注入 |

**原则：** 一个 Skill 服务所有企业，不 per-tenant 复制 Skill。

## 10. 内容工厂（M5）

### 10.1 一源多态

同一知识库事实 → 多种内容形态：

| 形态 | 渠道 | 模式 |
|------|------|------|
| 官网项目页 + FAQ + Schema | 官网 | AUTO |
| 知乎长回答 | 知乎 | SEMI |
| 小红书笔记 | 小红书 | SEMI |
| 点评/美团商家简介 | 点评/美团 | GUIDED |
| 项目对比表 | 官网/知乎 | SEMI |

### 10.2 内容质量要求

- 语义深度：直接回答用户问题，非关键词堆砌
- 可信度：数据有来源，案例可验证
- 结构化：FAQ Schema、LocalBusiness Schema、对比表

### 10.3 审核流程

```
Skill 生成 → 事实审查 → 合规审查 → 用户审核 → 发布
```

## 11. 发布中心（M6）

### 11.1 三种发布模式

| 模式 | 说明 | 渠道示例 |
|------|------|---------|
| **AUTO** | API 自动发布 | 企业官网、CMS |
| **SEMI** | 生成内容包 + 一键复制/导出 | 知乎、小红书、公众号 |
| **GUIDED** | 生成文案 + 操作指引 | 点评、美团、地图 POI、新氧 |

### 11.2 发布任务

- 记录：渠道、模式、内容、状态、发布时间、外链 URL
- 状态：draft → ready → published / failed
- 外链 URL 回填后供监测溯源

### 11.3 官网 AUTO 发布方案（已定）

**MVP 不做完整自建 CMS**，采用「发布适配器」模式，按优先级支持：

| 方案 | 说明 | MVP |
|------|------|-----|
| **平台托管页** | 平台生成落地页 + 固定 URL，自带 Schema | ✅ 主推 |
| **WordPress 对接** | 通过 REST API 发到客户已有 WP 站点 | ✅ 可选 |
| **易优 CMS 对接** | 通过 API 发到易优站点（国内 SME 常见） | V1.1 |
| **自建 CMS** | 平台内完整建站系统 | ❌ 不做，成本高、边界模糊 |

**区别简述：**
- **自建 CMS**：可控性最高，但要自己做编辑器、主题、Hosting，偏离 GEO 核心
- **WordPress**：全球普及，REST API 成熟，适合已有官网的客户
- **易优 CMS**：国内中小企业常见，PHP 生态，部分客户已在用
- **平台托管页**：客户零门槛，URL 归平台或绑定自定义域名；最适合 MVP 验证

客户无官网时 → 用平台托管页；已有 WP/易优 → 配置 API 一键推送。

### 11.4 MVP 不做

- 全自动发知乎/小红书/点评
- 代发评价、刷单
- 完整自建 CMS

## 12. 监测中心（M7）

### 12.1 监测逻辑

- 预设 Prompt 库（来自 Agent + 行业模板 + 用户补充）
- 定期向 AI 引擎提问（建议每周）
- 记录：品牌是否出现、排名、情感、引用 URL

### 12.2 MVP 监测引擎

**自建（必做）：** DeepSeek、豆包、Kimi、文心一言

**第三方（可选，per-tenant 配置）：** Otterly 等，用于海外引擎或补充

### 12.3 核心指标

| 指标 | 说明 |
|------|------|
| 品牌提及率 | 品牌出现在 AI 回答中的比例 |
| 推荐顺位 | 被推荐时排第几 |
| 引用来源 | AI 引用了哪些 URL |
| Share of Voice | 相对竞品的声量占比 |
| 情感倾向 | 正面 / 中性 / 负面 |

### 12.4 闭环

```
监测结果 → 缺口分析 → 反馈 Orchestrator → 新策略 → 用户确认 → 再生产
```

### 12.5 预期管理

- 不承诺具体排名
- 首效周期：4–8 周可见引用变化趋势
- 卖「认知资产建设 + 可见度趋势」，非「保证第一」

## 18. 风险与对策

| 风险 | 对策 |
|------|------|
| 第三方平台无法自动发 | SEMI/GUIDED 模式，诚实告知用户 |
| GEO 效果难量化 | 监测闭环 + 趋势报告，不承诺排名 |
| AI 幻觉 | 知识库约束 + 事实审查 |
| 生美合规 | 默认生美规则；医美机构启用加强规则，用户终审 |
| 行业包扩展成本 | 平台与行业包解耦，beauty 先跑通 |

## 19. 已定决策

| 议题 | 决策 |
|------|------|
| 官网 AUTO 发布 | MVP 主推**平台托管页**；可选对接 WordPress；易优 V1.1；不做自建 CMS |
| 痛点挖掘 | **多形式输入**：客户数据优先 → 手动/API → 定向爬虫补充 |
| 计费模型 | **内容按条数**消耗；**监测包月**（档位取决于自建 / 第三方 GEO） |
| 测试数据 / 合规默认 | **生美**；医美合规规则预留，按企业类型启用 |

### 19.1 计费模型（初版）

**内容计费：** 按生成 / 发布的**内容条数**扣费（FAQ、知乎稿、小红书笔记等各算 1 条，可在后台配置权重）。

**监测计费：** **包月订阅**，按监测策略分档：

| 档位 | 监测方式 | 说明 |
|------|---------|------|
| 基础版 | 自有监测（DeepSeek / 豆包 / Kimi / 文心） | 默认包含，prompt 数有限额 |
| 标准版 | 自有 + 更高 prompt 配额 + 更长历史 | 适合单店生美 |
| 高级版 | 自有 + 第三方 GEO（Otterly 等，per-tenant 可选） | 适合需海外引擎或多源对比 |

具体价格与条数配额边做边定；架构上内容钱包与监测订阅分离。

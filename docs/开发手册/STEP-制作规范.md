# STEP 制作规范

> **版本**：v1.2 | **日期**：2026-07-17
> **适用**：Claude Code（规划者 + 审查者）+ Cursor AI（执行者）

---

## 一、分工模型

```
用户 → 给任务方向
  ↓
规划者（Claude Code）→ 读代码 → 提问澄清 → 写 step 文件
  ↓
执行者（Cursor AI）→ 读 step 文件 → 自检 → 改代码 → 跑验收 → 回报
  ↓
审查者（同样是 Claude Code）→ 读 diff → 跑验收命令 → 直觉校验 → 通过/驳回
```

**核心原则**：step 文件是规划者和执行者之间的**接口契约**。写不清楚 = 执行者猜 = 质量事故。

---

## 二、规划者守则（Claude Code 用）

### 2.1 写 step 前自问（4 条，缺一不可）

在动笔写任何 step 文件之前，必须能回答：

1. **改动精确吗？** — 每个改动在哪个文件、哪几行（或哪个方法/函数），不能只有文件名
2. **输入输出明确吗？** — 执行者读完不需要额外推断业务逻辑，照做就行
3. **验收可执行吗？** — 验收标准是具体命令（curl / pytest / 浏览器操作），不是"功能正常"这种模糊话
4. **影响面清楚吗？** — 这个改动会不会破坏已有功能、是否需要配套 migration、前端后端的接口是否对齐

> **任一答不上来 → 向用户提问，直到能答上。不要硬写。**

### 2.2 数量限制

- 每轮最多写 **5 个** step 文件
- 每个任务（Ax）拆分的子 step **不超过 4 个**（A1-1 ~ A1-4）
- 每个 step 内的改动也尽量 ≤ 5 项（文件数或子任务数）
- **验收不占 step** — 验收是审查者的活，不是执行者的 step

### 2.3 命名规则

```
docs/开发手册/开发进度/steps/A{x}-{n}.md
```

- `{x}` = 任务编号（1, 2, 3...），与 TODO-A.md 对齐
- `{n}` = 步骤序号（1-4），按执行顺序排列

### 2.4 排序原则

Step 按**实际执行顺序**排列，不能出现"先验证后改代码"：

1. 🛠️ 改代码
2. 🔍 验证
3. 🆕 新建文件
4. 🧪 测试

**验收不排在这里** — 全部 step 完成后，审查者统一验收。同一个任务内，前面的 step 完成才能开始后面的。

### 2.5 规划者兼任审查者 — 验收前自检（3 条）

执行者改完代码回报后，规划者负责审查。审查不是走过场，必须带着"这个改动真能跑通吗"的质疑心态。

在勾选 step 完成之前，多问自己：

1. **抛开 step 文件，直觉上对不对？** — 有没有 step 没写到但感觉不对劲的地方。step 文件是我的盲区继承，不能因为"按 step 过了"就判通过。
2. **实际跑通了吗？** — 不接受执行者的截图/文字回报。要么我自己跑验收命令，要么让执行者给出可复现的命令 + 输出，我逐行对。
3. **有没有越权改动？** — git diff 涉及的文件必须与 step §2 涉改文件一致。🔍 只读文件如果被改了、B 轨代码被碰了、无关文件被顺手格式化，一律驳回。

> **3 条全过 = 验收通过。任一条触发疑问 → 驳回执行者，附具体原因。**

## 三、Step 文件模板

### 3.1 标准结构

```markdown
# Step Ax-n: 简短标题

> **所属任务**: Ax · 任务名
> **前置**: [Ax-(n-1)](./Ax-(n-1).md) | **后续**: [Ax-(n+1)](./Ax-(n+1).md)
> **类型**: 🛠️ 修改 | 🔍 验证 | 🆕 新建 | 🧪 测试

---

## ⚠️ 执行前自检（必须全部 ✅ 才能动手）

- [ ] 我知道要改**哪个文件的哪几行**（或哪个方法/函数）
- [ ] 我知道改动前后的**行为差异**（输入 → 输出）
- [ ] 我能在改完后跑**哪条命令**来验证
- [ ] 我有把握不碰到无关代码，或知道影响范围

> **如果任一未勾选 → 不要动手，向用户提问直到全部能勾选。**

---

## 1. 目标

一句话说清楚这个 step 要达成什么。

## 2. 涉改文件

| 文件 | 权限 | 说明 |
|------|:----:|------|
| `path/to/file.py` | 🛠️ | 改什么 |
| `path/to/readonly.py` | 🔍 | 只读参考 |

权限：🛠️(修改) | 🔍(只读) | 🆕(新建) | 🗑️(删除)

## 3. 改动清单

### 3.1 改动 1：标题

**文件**：`path/to/file.py`

**位置**：第 X-Y 行 / `function_name()` 方法内

**改什么**：（简单改动一句话描述；关键改动给出代码示例）

```python
# 关键改动才给完整代码，简单改动只描述
```

### 3.2 改动 2：标题

...（重复，总共不超过 5 项）

## 4. 不可破坏的约束

- ❌ 禁止改什么
- ⚠️ 注意什么边界

## 5. 验收标准

- [ ] 具体可执行的验证命令或操作
- [ ] 明确的期望输出
```

### 3.2 什么时候给完整代码

| 情况 | 做法 |
|------|------|
| 重写整个方法 | 给完整代码 |
| 改方法签名 / 返回值结构 | 给完整代码 |
| 删端点 + 重写路由 | 给完整代码 |
| 加新的数据库约束 | 给完整代码 |
| 加一行 / 删一行 / 改参数 | 只描述 |
| 和现有代码结构一致、照抄即可 | 只描述 |

### 3.3 step 类型标记

| 标记 | 含义 |
|:----:|------|
| 🛠️ | 修改现有代码（文件已存在） |
| 🆕 | 新建文件 |
| 🔍 | 只读验证，不改代码 |
| 🧪 | 运行测试 + 编写测试 |

## 四、80% 把握约束

### 4.1 规则

**step 文件的目标**：让执行 AI 读完能 100% 确定要做什么，不需要猜。

**规划者**：写 step 前，自己对每个改动有 80% 以上把握（知道文件路径、行号范围、改法），否则先问用户。

**执行者**：读 step 后，先过自检 4 条。如果有一条不能勾选 → 向用户提问。只有全部能勾选才能开始改代码。

### 4.2 举例

| 自检题 | ❌ 不能勾选的情况 | ✅ 能勾选的情况 |
|--------|------------------|----------------|
| 知道改哪个文件的哪几行 | "改登录逻辑" — 文件都没指定 | "改 `auth.py` 第 39-63 行，删除 OAuth2 表单登录" |
| 知道行为差异 | "优化登录" — 输入输出没说 | "改前：/login 走 OAuth2 表单；改后：/login 收 JSON body {email, password}" |
| 知道怎么验证 | "确认功能正常" — 太模糊 | "`curl POST /login -d '{...}'` → 期望 200 + access_token" |
| 知道影响范围 | "可能影响前端" — 不确定 | "只改后端路由，前端 `auth.ts` 已经发 JSON，无影响" |

## 五、禁止事项

### 规划者禁止

- ❌ 不读代码就写 step（必须先 Read/Grep）
- ❌ 一次写超过 5 个 step
- ❌ 一个任务（Ax）拆超过 4 个子 step
- ❌ step 里只有文件名没有方法名/行号
- ❌ 验收标准写"功能正常"这种废话
- ❌ 先验证后改代码的顺序错误

### 执行者禁止

- ❌ 跳过自检直接动手
- ❌ 自检不过还硬写代码
- ❌ 改 step 里没列出的文件
- ❌ 改了代码不跑验收就声称完成

## 六、todo 联动

每次写完 step 文件后，同步更新 `TODO-A.md` 对应任务的子项：

```markdown
- [ ] **[Ax-1](./steps/Ax-1.md)** — 🛠️ 描述
- [ ] **[Ax-2](./steps/Ax-2.md)** — 🛠️ 描述
- [ ] **[Ax-3](./steps/Ax-3.md)** — 🔍 描述
- [ ] **[Ax-4](./steps/Ax-4.md)** — 🧪 描述
```

> 验收不占 step。全部 4 个 step 完成后，由审查者统一验收 + 更新进度表。

## 七、执行记录与审查反馈（两个 AI 的共享通道）

### 7.1 文件位置

```
docs/开发手册/开发进度/执行记录/Ax.md
```

每个任务一个文件，如 `A1.md`、`A2.md`。

### 7.2 执行者写（每步追加）

```markdown
## Ax-n · YYYY-MM-DD HH:MM

- **改了什么**：文件 + 改动描述
- **验收结果**：验收命令 + 关键输出
- **遇到问题**：无 / 具体问题
```

### 7.3 审查者读 + 写

审查者从执行记录读"改了什么"和"验收结果"，对着 git diff 验证，然后追加审查结果：

```markdown
## 审查 · YYYY-MM-DD HH:MM

**Ax-1** ✅ 通过
**Ax-2** ✅ 通过
**Ax-3** ❌ 驳回 — <具体原因，指向哪个文件哪行>
**Ax-4** ⏳ 等待 Ax-3 修复后重跑
```

### 7.4 执行者修复后追加

```markdown
### 修复 · YYYY-MM-DD HH:MM

- **审查意见**：<引用驳回原因>
- **修复了什么**：<文件 + 改动>
- **验收结果**：<重新跑验收>
```

### 7.5 审查者最终确认

```markdown
### 二次审查 · YYYY-MM-DD HH:MM

**Ax-3** ✅ 通过（修复确认）
**Ax-4** ✅ 通过
**全任务通过** → 更新进度表 + 勾 TODO-A + NOTIFY
```

## 八、检查清单

### 写 step 前（规划者自检）

```
[ ] 我读了所有要改的文件
[ ] 每个改动我知道文件路径 + 方法名/行号范围
[ ] 每个 step 不超过 5 项改动
[ ] 一个任务不超过 4 个 step
[ ] 执行顺序正确：改代码 → 验证 → 测试
[ ] 验收标准是具体命令，不是模糊描述
[ ] 自检 4 条放在 step 文件开头
[ ] 关键词：关键改动给代码，简单改动只描述
[ ] 最后一个 step 是 🧪 测试，不是 ✅ 验收
```

### 审查时（规划者兼审查者自检）

```
[ ] 直觉上对不对 — step 没写到的边界有没有问题
[ ] 实际跑通了吗 — 自己跑了验收命令，不看截图
[ ] 越权了吗 — git diff 只涉及 step §2 文件，🔍 文件未被改
```

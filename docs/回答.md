# 五答（简洁版）

---

## 1. 转化闭环要怎么做？之前有个案例是「归因算法」

**转化闭环** = 不只看「AI 有没有提到我」，还要看「提到之后有没有人来咨询/到店/成交」，并把结果反馈到下一轮写什么。

**MVP 能落地的做法（生美）：**

| 环节 | 做什么 |
|------|--------|
| 记录 | 托管页访问量、留资表单；小红书/点评私信数（老板每周填或授权后自动拉） |
| 关联 | 每条内容带 `content_asset_id`，发布时记渠道+日期 |
| 归因（简化版，不是大厂那种复杂算法） | 同一周内：某篇小红书发布后 → 咨询量是否上升；或顾客说「豆包/小红书看到的」 |
| 反馈 | 若 **AI 提及高但咨询为 0** → 下一轮少加篇数，改补 **案例/FAQ/评价类** 内容，而不是再发 5 篇 |

**和 FrontMind「归因算法」的关系：** 大厂用多触点模型；我们 MVP 用 **「内容 ID + 时间窗口 + 老板确认」** 就够。先跑通「写了什么 → 有没有人来问」，再迭代算法。

## 2. 「article_count + 按条计费 → 铺量」——信源权重页该怎么改？

**问题：** 现在逻辑像「小红书 cite 高 → 默认写 3 篇 → 按条收钱」，容易变成刷量工厂。

**改法（思路）：**

```
旧：先定「每个渠道写几篇」→ 再填选题
新：先定「要回答哪几个 scenario（场景问题）」→ 再映射到渠道，篇数 = scenario 数量上限
```

**信源权重页改表述：**

| 列 | 旧含义 | 新含义 |
|----|--------|--------|
| 权重 | 渠道重要性 | 不变：AI 更爱引哪类源 |
| 篇数 | 本轮写几篇 | 改为 **「本渠道承接几个 scenario」**（默认 ≤ 痛点勾选数，总量建议 3～5） |

**计费：** 可以保留按条，但产品引导写 **「本轮建议 3 个场景 × 各 1 渠道 = 3 条」**，而不是「小红书 5 篇」。条数是结果，不是目标。

## 3. 词库不应该像 SEO 中心吗？Core 池是什么？scenario-first 什么意思？

**词库（KeywordLibrary）** 仍然需要，但角色要变：

| | SEO 思维 | GEO 思维（scenario-first） |
|--|----------|------------------------------|
| 生产起点 | 关键词「皮肤管理 价格」 | 场景问法「敏感肌能不能做皮肤管理」 |
| 词的作用 | 标题堆砌、排名 | 监测用 prompt、title/summary **槽位**，辅助曝光 |
| 成功标准 | 词有没有排名 | AI 能不能 **正确回答这个场景** |

**Core 池是什么？**  
监测用的 **固定问题清单**。每周用同一批问题去问豆包/DeepSeek 等，看品牌有没有被提到、你的链接有没有出现在引用里。

- **现在设计：** Core 池主要来自 KeywordLibrary（偏词）  
- **建议改：** Core 池主要来自 **pain_clusters / scenario**（偏问法），词库只作标签和槽位

**所以：** 词库不是删掉，而是 **降级为辅助**；**主单元是 scenario（content_unit）**，不是一词一文。

## 4. 「信任资产（trust_asset）」是什么？

**信任资产** = 让顾客和 AI **敢信你** 的可验证材料，不是泛泛的软文。

| 类型 | 例子 | 和现在的关系 |
|------|------|--------------|
| 案例 | 「张女士敏感肌 3 次护理后…」（有过程、可核对） | 现有 Cases[]，但缺专门生成流程 |
| 标准问答 | 「做清洁会伤皮肤吗？」+ 基于项目的标准答 | 现有 FAQs[] |
| 可引用证据 | 门店 NAP、项目价格区间、资质 | Brand/Stores/Services |
| 客户原话 | 美团/客服里的真实评价（整理后） | RawInputs → 升格进 Fact |

**「独立产线」指：** 不要只走「写小红书」一条线，而是先产 **trust_asset** → 审过进 KB → 再被各渠道内容 **引用**。

```
trust_asset（案例/FAQ/证据块）→ 审过入 KB
         ↓
content_unit（小红书/托管页/知乎）引用这些 asset 写稿
```

这样写的是 **有据可查的推广**，不是空口软文。对应你一开始说的「内容可信度」。

## 5. 「thin KB 无增量诊断」「KB 厚度 / gap 评分」是什么意思？

**thin KB（薄知识库）** = 库里只有店名、电话、两三个项目名，没有案例、没有 FAQ、没有评价。

- 系统 **不会胡编**（fact_verify 拦住）  
- 但写出来的东西 **很空、没信息量** → AI 仍然不爱引用你  

**KB 厚度评分（通俗说）：** 给知识库打个「饱满度分」，告诉老板还缺什么。

| 检查项 | 有/无 |
|--------|-------|
| 门店 NAP 完整 | |
| ≥3 个项目含价格/时长 | |
| ≥2 条可发布案例 | |
| ≥5 条 FAQ | |
| ≥10 条 RawInputs（评价/客服） | |
| 竞品录入 | |

分数低 → 策略页提示：**「先补案例/FAQ，再生成内容」**，而不是硬生成 5 篇水稿。

**gap 评分（和 diagnose 结合）：**  
信源诊断发现 AI 回答常引用「小红书测评、点评榜单」→ 对比你的 KB：**缺测评型案例？缺对比 FAQ？** → 列出 **content_gaps[]**（内容缺口清单），Orchestrator 优先补这些，而不是盲目加篇数。

**一句话：** 厚度 = 你库里有几斤几两；gap = AI 爱引的那类信息你还缺哪几块。
